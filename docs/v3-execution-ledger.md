## 1. Authority and proof rules

The Ultra roadmap controls product scope, phase order, gate meanings, estimates, and the definition of done. Stable requirements in `requirements/requirements.md`, declared cases in `requirements/test-cases.md`, and `requirements/traceability.json` control normative coverage. This ledger controls work-package order and status only. It does not replace requirements, executed evidence, or owner authorization.

Use these status values exactly:

| Status                     | Meaning                                                                                                    |
| -------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `verified-current-dirty`   | Executed on the current development tree, but not frozen, retained, hosted, deployed, or release evidence. |
| `verified-historical-only` | Executed for an older recorded source or artifact identity and must not be reused for changed bytes.       |
| `selection-required`       | Kato must choose or revise the proposed design before implementation.                                      |
| `open-local`               | Safe local engineering remains after its prerequisites pass.                                               |
| `authority-required`       | Commit, push, account, provider, deployment, billing, or publication authority is required.                |
| `external-evidence-needed` | An external party or platform must supply evidence that local implementation cannot establish.             |
| `not-started`              | The work has no current implementation or executed acceptance evidence.                                    |

No traceability row, linked test file, generated build, dry run, plan, or passing test from a different source identity proves a gate. A receipt counts only when it binds the exact requirement and test IDs, source and artifact identities, configuration, command, environment, time, result, and evidence boundary.

## 7. Receipt contract

Every accepted automated, manual, hosted, provider, platform, or release receipt must record:

- gate, requirement, and test IDs;
- start, end, duration, command, runner, operating system, browser, viewport, and relevant hardware profile;
- dirty-tree base HEAD plus source-content digest for development evidence, or the exact committed SHA for frozen, hosted, and release evidence, together with client, Worker, map, schema, replay, Lab, rollback, SBOM, checksum, and provenance digests;
- non-secret build target, provider mode, bindings, policy identity, region set, cadence, limits, and test profile;
- artifact input and canonical output paths, immutable selected-input and private-execution identities, retry count, warning/failure details, reviewer disposition, and rollback identity;
- whether the result is local dirty-tree, historical, retained-candidate, hosted, physical-platform, provider, deployed, or public evidence.

The verifier must reject missing, pending, stale, linked-but-unexecuted, wrong-source, wrong-artifact, rebuilt, privacy-unsafe, or manually overridden mandatory evidence.
